# Decisions

Short ADRs: context, decision, alternatives discarded.

## ADR-001: Monorepo with Core / Infrastructure / Api split
- **Context:** The agent logic (tools, tracing, language detection) should be testable without the web host.
- **Decision:** `Chatbot.Core` (domain, agent, tools, no web deps), `Chatbot.Infrastructure` (EF Core, LLM client, seed), `Chatbot.Api` (endpoints, DI). Revisit and merge Core + Infrastructure if the split proves excessive.
- **Alternatives:** single project (simpler, but the agent would be tied to ASP.NET and EF).

## ADR-002: Slot capacity via an atomic conditional UPDATE
- **Context:** Two visitors can try to take the last seat of a slot at the same time. A read-check-write in application code (or the model deciding "there is room") would oversell it.
- **Decision:** Capacity is enforced by PostgreSQL in two layers. (1) `SlotBooking.TryReserveAsync` runs a single statement, `UPDATE availability_slots SET "Booked" = "Booked" + 1 WHERE "Id" = @id AND "Booked" < "Capacity"`, and returns `true` only if one row was updated. The row lock serializes concurrent callers, so exactly `Capacity` of them win. (2) CHECK constraints `ck_availability_slots_booked_lte_capacity`, `..._booked_non_negative` and `..._capacity_positive` make an invalid state impossible even if some code path bypasses the method. Idempotency is a unique index on `Booking.IdempotencyKey`; `TraceEvent.Type` is a string column with a CHECK over the closed enum. Verified by concurrency tests (10 parallel callers, capacity 1 and 3) against a real PostgreSQL 17 (Testcontainers).
- **Alternatives:** optimistic concurrency with a row version (needs a retry loop and surfaces `DbUpdateConcurrencyException` to the tool for a case that is just "slot full"); `SELECT ... FOR UPDATE` in a transaction (two round trips and a longer lock); an in-process lock or semaphore (breaks with more than one API instance, and the database would not be the source of truth).
- **Consequences:** `Booked` must only change through `TryReserveAsync` (and a future release method that decrements with `WHERE "Booked" > 0`). Reserving the seat and inserting the `Booking` must share one transaction so a failed insert (e.g. duplicate idempotency key) rolls the seat back.

## ADR-003: Data model conventions
- **Ids:** `Guid` everywhere, generated client-side as UUIDv7 (`Guid.CreateVersion7()`), so ids are time-ordered, index-friendly and can be assigned before `SaveChanges` (the seed can build whole graphs with fixed ids). `ModelPricing` is keyed by `Model`.
- **Time:** `DateTimeOffset` in UTC, mapped to `timestamptz`.
- **Enums:** stored as strings (readable rows, safe to reorder the enum).
- **jsonb:** `JsonElement` (nullable where optional) for `Offering.Attributes`, `Booking.Items` and `TraceEvent.Input/Output`; `List<string>` for `Business.QuickReplies`. Natively supported by Npgsql with no converters, keeps Core free of EF, and `EF.Functions.JsonContains` (backed by a GIN index on `Attributes`) covers the `search_catalog` filters.

## ADR-004: Tools, agent service, tracing and LLM client live in Infrastructure
- **Context:** ADR-001 planned the agent and its tools in `Chatbot.Core`. But every tool needs the database (`ChatbotDbContext`, the atomic `SlotBooking.TryReserveAsync`, a transaction around seat + booking), and the tracing layer persists `TraceEvent`s. Putting them in Core would force Core to reference EF Core, or hide the database behind repository interfaces that would only exist to be mocked.
- **Decision:** `Chatbot.Core` keeps only pure, dependency-free logic: the domain, language detection, phone masking, cost calculation and prompt text (`Chatbot.Core.Agent`). Tools (`AgentToolFactory`, `ToolContext`), `AgentService`, the tracing `DelegatingChatClient`s and the LLM client with its fallback (`Chatbot.Infrastructure.Agent`, `Chatbot.Infrastructure.Llm`) live in `Chatbot.Infrastructure`. The tools are tested against a real PostgreSQL (Testcontainers), not an in-memory fake, because the rules they must guarantee (capacity, idempotency, jsonb filters) are database behaviour.
- **Alternatives:** tools in Core behind `IBookingRepository`-style interfaces (more indirection, and the concurrency guarantee would be tested against a fake that cannot prove it); merging Core and Infrastructure now (ADR-001 still keeps the split because the pure logic is the part worth unit-testing without a container).
- **Consequences:** Core never references EF Core or Microsoft.Extensions.AI. The tools take the business and session from a server-built `ToolContext`, never from model arguments, and are created per request around that request's single `DbContext`. `create_booking` also checks in code that the customer's name and phone appear in the session's own user messages (`customer_data_not_provided`), because a real model, after an injected "no name or phone needed", booked as `Valued Patient` with an invented number.

## ADR-005: Trace storage and masking
- **Context:** The trace is public (any visitor sees the steps of their own run, SPEC 7.5) and a conversation about a booking contains phone numbers. It also feeds the cost numbers, so it has to agree with the run totals, and the UI needs the same JSON live (SSE) and after a reload.
- **Decision:** (1) One `TraceRecorder` per run is the only writer: it allocates `Sequence` in completion order, prices each `LlmCall` (`tokens x ModelPricing`, rounded to 8 decimals, stored in `trace_events.CostUsd`) and accumulates the run totals, so `AgentRun.CostUsd` is by construction the sum of its `LlmCall` costs. (2) Events are built from three hooks: `TracingChatClient` below function invocation (one `LlmCall` per model call, completed when its stream ends or fails), `FunctionInvokingChatClient.FunctionInvoker` (one `ToolCall` per invocation; a rejected rule or a successful handoff adds a `Guardrail`/`Handoff` event) and the run itself (`iteration_limit`, `agent_error`, `agent_cancelled`). (3) The recorder holds the events in memory, `AgentService` streams each new one as `AgentEvent.Trace` between tokens, and they are saved in the same `SaveChanges` that closes the run. (4) Every payload goes through `TracePayload`: phone numbers are masked in all JSON strings (and in numbers that look like a phone) and a payload over 4096 characters of JSON becomes a marked preview of its first 4096 characters. Masking runs before truncation so a number cut by the limit does not leak. Free text inside an `LlmCall` is clipped (1000 characters per input message, 2500 for the output text) before the global limit, so one long answer does not hide the provider and model fields. Exception messages are never stored, only the type and HTTP status. (5) `Booking.CustomerPhone` keeps the full number; the admin list masks it unless `Admin:MaskPhones` is `false`. The provider that answered is stored in `output.provider` of each `LlmCall` (the run's `provider` is derived from them), so no column was needed.
- **Alternatives:** persisting each event as it happens (a second `DbContext` or interleaving saves with the tools' own `SaveChanges`, and a failed tool leaves half-saved entities in the shared context; the price is that a killed process leaves no trace for that run, which already reads `Error`); masking only when reading (the unmasked number would sit in the table and every future reader would need to remember); computing event costs when reading (a pricing change would rewrite history); an OpenTelemetry exporter (heavier than a demo needs and the public panel still needs the sanitized copy).
- **Consequences:** A trace never contains a phone number, but other personal data a visitor types (a name) stays in the user message and tool arguments, so the public README should say the demo is not for real personal data. A new tool error code that should count as a guardrail must be added to `ToolCallTracer` (`invalid_*` already is).

## ADR-006: Layered abuse limits, counted where they must survive
- **Context:** The demo is public and each message costs real tokens. SPEC 9 asks for limits per IP, per session and per day, a restricted CORS and no secrets in the repo. The limits have different jobs: slow one noisy client, end a conversation, bound the total bill.
- **Decision:** (1) The per-IP limits are `Microsoft.AspNetCore.RateLimiting` sliding windows (30 messages, 20 new sessions and 60 admin requests per 10 minutes by default), in memory, attached to the two POST endpoints and the admin group (the last one bounds guessing `X-Admin-Key`). (2) The per-session limit (25 user messages) and the global daily cap (500 agent runs per UTC day) are an endpoint filter that counts `chat_messages` and `agent_runs` rows, so they survive restarts, are shared by instances, and cannot be dodged by rotating IPs; the daily count is served by a new index on `agent_runs.StartedAt`. All refusals happen before a run exists and answer 429 with `{message, code}` (`ip_rate_limit`, `session_limit`, `daily_cap`) and `Retry-After` when waiting helps. (3) The client IP is the connection peer unless the peer is in `Security:TrustedProxyCidr`, in which case the last `X-Forwarded-For` entry is used (`ForwardLimit` 1); a blank list trusts nobody and does not add the middleware, because an empty list in ASP.NET means "trust everyone". (4) CORS is an explicit list of origins, two methods and three headers; wildcards and zero or negative limits fail at startup rather than weaken a cap. (5) Cost caps stay in `AgentOptions` and are validated at startup.
- **Alternatives:** a Redis or Postgres backed limiter for the IP window (more moving parts, and the IP limit is only a speed bump: the database limits already bound the cost); counting requests in memory for the daily cap (resets on every restart, so a crash loop would reset the budget); a counter table (a second source of truth that can drift from the rows that are the real usage); `AllowAnyHeader`/`AllowAnyMethod` CORS (not needed, and wider than the frontend uses); recording HTTP-level rejections as `Guardrail` trace events (there is no run to attach them to).
- **Consequences:** The per-IP window is per API instance and resets on restart. A burst of concurrent requests can pass a database limit by a few messages (count then insert is not atomic). Trusting private ranges by default is a convenience for docker compose and a spoofing risk wherever the API is reachable directly from those ranges; the production value must list only the real proxy. IPv6 clients are counted by /64 so one connection cannot rotate through its addresses.


## ADR-007: No RAG: the catalog is searched with filters
- **Context:** Each business has 9 or 10 offerings (28 in total) with a name, a description, a price and a few structured attributes (neighborhood, rooms, category, gluten-free). SPEC 4 puts RAG and vector stores out of scope and asks for the reason to be written down.
- **Decision:** `search_catalog` is an ordinary query over the session's business: optional text terms matched with `ILIKE` on name and description (at most 8 terms), `minPrice`/`maxPrice`, `kind`, and attribute filters matched by `jsonb` containment (`EF.Functions.JsonContains`, GIN index on `Attributes`). It returns at most 5 offerings ordered by price. `get_offering_details` loads one by id. The prompt requires prices and availability to come from these tools in the same run, not from the model's memory, and the evals check it.
- **Alternatives:** embeddings in `pgvector` (an extra component, an embedding model to call and keep in sync, and approximate matches that can return the wrong item or a wrong price for "a 2-room in Palermo under 600", which is an exact filter); putting the whole catalog in the system prompt (works at this size, but prices would be answered from memory instead of from a tool call in the run, and the trace could not show where a number came from); full-text search (`tsvector`: more machinery than `ILIKE` for 28 rows).
- **Consequences:** Free-text matching is literal: a synonym that is in neither the name nor the description is not found, and the model has to retry with other terms or filter keys. Revisit when a catalog has hundreds of items or long documents (policies, FAQs) where the question cannot be turned into filters. M8 did that for free text only, in a separate path (ADR-015); the catalog is unchanged.

## ADR-008: Critical rules live in code, the model only chooses what to do
- **Context:** The conversation is controlled by the model, which is good at reading free text and bad at arithmetic, at knowing whether a slot has room and at resisting a user who tells it to ignore its instructions. A wrong answer here is a double-booked slot, a wrong order total or a leak across businesses (SPEC 7.4).
- **Decision:** The rules that cannot fail are enforced by the server and the database, and the model cannot override them: (1) scoping: every tool gets the business and session from a server-built `ToolContext`, never from arguments, and another business's id is answered as "not found" (ADR-004); (2) idempotency: a unique `Booking.IdempotencyKey` derived from session + slot or items (ADR-002); (3) totals: `create_booking` computes an order total from catalog prices and quantities, the model sends no price; (4) capacity: the atomic `UPDATE ... WHERE "Booked" < "Capacity"` and CHECK constraints (ADR-002); (5) bookings are created as `PendingConfirmation`, so the code cannot produce "confirmed"; (6) caps: `MaxIterations`, `MaxOutputTokens`, input length, history window and the rate limits (ADR-006); (7) invalid tool arguments return a readable error to the model instead of throwing, and the rejected rule is recorded as a `Guardrail` trace event. The prompt asks for the same behavior (confirm before booking, say "pending", no prices from memory), and the evals check it, but nothing depends on the model obeying.
- **Alternatives:** a prompt-only approach as in the first version of this project (a "registered your visit" that is only text, a handoff parsed from a tag in the output, a rate limit in the browser); letting the model pass `businessId` or a price and validating after (more checks to forget, and a larger surface for prompt injection); a separate "validator" model (slower, costs tokens and is still probabilistic).
- **Consequences:** The model can still choose the wrong tool or ask the visitor the wrong question; that is what the evals measure. `PromptInjectionTests` replays a model that obeys an attacker and asserts nothing leaks and nothing is written. Real-model injection cases (6 in `evals/cases/injection-gibberish.yaml`) have not been run yet.

## ADR-009: SSE over `fetch` + `ReadableStream`, not WebSockets or `EventSource`
- **Context:** An answer is a stream of events (tokens and trace steps) that flow only from the server to the browser. The message is sent with a POST and a body (`{ text }`) on a session id in the path, and the endpoint must also answer plain 4xx/429 JSON before streaming starts.
- **Decision:** `POST /api/sessions/{id}/messages` answers `text/event-stream` (`event:` + one line of JSON `data:`; flushed per event; `Cache-Control: no-cache`, `X-Accel-Buffering: no`). The browser reads it with `fetch` and a `ReadableStream`, through a small incremental parser (`web/src/api/sse.ts`, unit tested with events split at arbitrary chunk boundaries). Cancelling is an `AbortController`. nginx forwards `/api/` with `proxy_buffering off`.
- **Alternatives:** the browser `EventSource` (GET only: no body, no custom headers such as `X-Admin-Key`, and it reconnects on its own, which would re-send a message that costs tokens; the message would have to travel in the URL or be created by a first request and streamed by a second); WebSockets (bidirectional and stateful, which the traffic does not need, with no use of HTTP status codes and middleware such as the rate limiter and CORS, and sticky connections to manage); long polling (more requests and no incremental tokens).
- **Consequences:** The client owns the parser, and unknown event names are ignored so the contract can grow. There is no automatic reconnect: a dropped stream is an error the visitor can retry, and the server closes the run as `Error` (`agent_cancelled`) when the client leaves. The same JSON is used for the live `trace` event and for `GET /api/sessions/{id}/trace` after a reload.

## ADR-010: Provider fallback only before the first token, one retry, no SDK retries
- **Context:** The default setup is two free-tier OpenAI-compatible providers (Gemini primary, Groq fallback), and free tiers answer 429 or 5xx often. A visitor should not see an error if the other provider is available. But once a token has been streamed, switching provider would mix two answers.
- **Decision:** `FallbackChatClient` wraps the primary and an optional fallback. A call that fails with HTTP 429 or any 5xx (`IsRetryable`) is retried **once** on the fallback. In streaming the first update is pulled before deciding, so the fallback is used only while nothing has been yielded; after that errors propagate and the run ends with an `error` event. Other 4xx errors (400, 401) are our bug or configuration and are not retried. Each provider gets its own model name (`WithModel`), and every update is tagged with `llm.provider` and `llm.model`, so the trace and the cost show which one answered each call. The fallback exists only if `Llm:Fallback:ApiKey` is set. When it exists, the primary's OpenAI SDK client is created with `ClientRetryPolicy(0)`: the SDK would otherwise retry 429/5xx up to 3 times with backoff before the exception reaches us, so we would wait on the failing provider instead of switching. Without a fallback the SDK keeps its default retries. A missing primary key does not stop the app at startup; the first chat call fails with an actionable message.
- **Alternatives:** keeping the SDK retries and then falling back (the visitor waits through the backoff first); retrying the same provider; trying the fallback after a mid-stream failure (the visitor would see a half answer followed by a different one, and tool calls could be repeated); a circuit breaker or a provider rotation (more state than a demo with two providers needs).
- **Consequences:** A failure after the first token is not recovered, only reported. The fallback is per model call, not per run: in one run the primary can answer one call and the fallback another, so `AgentRun.Model` lists the models in order of first use and each `LlmCall` has its own provider. Covered by `FallbackChatClientTests` and `LlmClientFactoryTests` with scripted clients; it has not been exercised against two real providers.
- **Unknown finish reason:** Gemini sometimes ends a response with `finish_reason: "function_call_filter: MALFORMED_FUNCTION_CALL"` (the model failed to build a tool call). The OpenAI SDK cannot map it and throws `ArgumentOutOfRangeException` ("Unknown ChatFinishReason value") while deserializing, which used to kill the run. It is non-deterministic and usually succeeds when repeated, so `FallbackChatClient` repeats the call once on the same provider and, if that fails too, falls back like for a 429/5xx. Same rule as above: only while nothing was yielded; later it propagates. Detected by exception type and message (`IsUnknownFinishReason`), because the SDK has no dedicated exception.

## ADR-011: Cost per model call, priced with a `ModelPricing` table
- **Context:** The trace panel shows what each answer cost. The free tiers charge nothing, but the project should show what a run would cost at paid rates, and tariffs change.
- **Decision:** `ModelPricing` has one row per model (`InputPerMillionUsd`, `OutputPerMillionUsd`). The `TraceRecorder` prices every `LlmCall` with `CostCalculator`: `(tokensIn x input + tokensOut x output) / 1,000,000`, using the row of the model that answered that call (the fallback can answer one call of a run and the primary another), rounded to 8 decimals and stored in `trace_events.CostUsd`. The run cost is the sum of its `LlmCall` costs, so the numbers agree by construction (since M8 the run total also includes the embedding cost of each `Retrieval` event: the total is the sum of every event cost). Tokens come from the provider's usage report (`UsageContent` in streaming). A model without a row costs 0. Only one row is seeded (`gemini-3.5-flash-lite`, from the public price page on 2026-10-09); the Groq models have no public price and are inserted by hand. The model is configuration, the price is data.
- **Alternatives:** per-run cost from the sum of tokens (wrong as soon as two models answer one run); tariffs in `appsettings` or in code (a price change would need a deploy, and old events would be recomputed with the new price); computing the cost when reading (a pricing change would rewrite history, ADR-005); reading the bill from the provider (not available per call, and free-tier calls bill 0).
- **Consequences:** Costs of models without a row show as `0` rather than "unknown", so a new model needs its row to appear in the panel. The stored cost is a tariff estimate, not an invoice. Tokens of a call that failed before usage was reported are not counted.

## ADR-012: Tracing sits below function invocation
- **Context:** One user message can take several model calls: the model asks for a tool, the tool runs, and the model is called again with the result (up to `MaxIterations` tool rounds, so up to N + 1 calls). The trace has to show each of these calls with its own tokens, latency and provider, because that is where the cost and the delay are.
- **Decision:** The pipeline is built with `ChatClientBuilder`, whose first registration is the outermost client: `UseFunctionInvocation` outermost, then `TracingChatClient`, then the keyed `llm` client (`FallbackChatClient`). Because the tracer is *below* the function-invoking client, it sees every individual call that goes to the provider (and the `llm.provider`/`llm.model` tags the fallback adds); a run with two tool rounds produces three `LlmCall` events. Tool calls are recorded through the `FunctionInvoker` hook of `FunctionInvokingChatClient` (`ToolCallTracer`), which wraps the call of each tool that really runs. Guardrail and handoff events are derived from the tool's own result.
- **Alternatives:** the tracer above function invocation (it would see one call and one final response per user message, hiding the intermediate calls, the tokens spent on them and the model's tool requests); a decorator around each `AIFunction` (needs one per tool, and still gives nothing about model calls); OpenTelemetry instrumentation of `IChatClient` (heavier, and the public panel still needs sanitized, persisted events, ADR-005).
- **Consequences:** The order of the builder calls is the design: moving `.Use(TracingChatClient)` above `UseFunctionInvocation` would make the trace show one `LlmCall` per user message instead of one per model call. `TracingTests` asserts the interleaved `LlmCall`/`ToolCall` sequence of a scripted booking flow. Events are numbered in completion order, so a `ToolCall` appears between the `LlmCall` that asked for it and the one that follows.

## ADR-013: Gemini 3 thought signatures: replay Google's sentinel on tool calls
- **Context:** Gemini 3 models, through the OpenAI-compatible endpoint, return a `thought_signature` on each tool call (`tool_calls[].extra_content.google.thought_signature`) and answer HTTP 400 ("Function call is missing a thought_signature in functionCall parts") if the next request replays that assistant message without it. `Microsoft.Extensions.AI.OpenAI` does not keep `extra_content` when it converts history back to the wire format, so the second model call of every tool loop failed, and so would a later turn rebuilt from stored tool exchanges. The 2.5 models, which do not need it, are no longer available to new keys.
- **Decision:** `GeminiThoughtSignaturePolicy`, a `System.ClientModel` `PipelinePolicy` registered per call with `OpenAIClientOptions.AddPolicy`, rewrites the outgoing `chat/completions` body: every tool call of every assistant message that has no `extra_content.google.thought_signature` gets Google's documented sentinel `skip_thought_signature_validator` (meant for history that was not produced in this generation). A real signature, if present, is kept. It is added only when the provider host is `generativelanguage.googleapis.com` (`AddTo`), so Groq and any other provider never see the field. Bodies without `tool_calls` are not parsed or modified, so the first call of a run costs a byte search only. Streaming and non-streaming take the same path.
- **Alternatives:** persist the real signatures with each tool call and replay them (the right fix for quality, but it needs a column on the tool exchange rows and a way to read `extra_content` from the response, which the MEAI conversion also discards; discarded for complexity); stay on a model that does not need signatures (no longer possible); a `DelegatingHandler` on `HttpClient` (works, but string-edits JSON below the SDK and cannot tell the endpoint apart as cleanly as a policy).
- **Consequences:** Google documents that the sentinel can lower reasoning quality in multi-step tool use, because the model cannot recover its previous thoughts. The agent's tool loops are short (a few rounds), so this is accepted for the demo. Revisit and persist real signatures if evals show tool-use regressions on Gemini. Covered by `GeminiThoughtSignaturePolicyTests` with a recording transport (rewrite on the Gemini host, none on Groq, real signature kept, other messages and endpoints untouched, streaming included); it has not been exercised against the real endpoint by the tests.

## ADR-014: One system message; the language instruction is its last paragraph
- **Context:** SPEC 7.3 asks for the language instruction as the *last system message*, so the model reads it right before answering. Gemini's OpenAI-compatible endpoint silently drops system messages when a request contains more than one `system` message. It does not fail: it answers without the persona, the rules and the current date. Verified with raw `curl` on both `[system persona, user, system language]` and `[system, system, user]`; a single merged system message works.
- **Decision:** `AgentService` sends exactly one system message, always first: `PromptBuilder.BuildSystemPrompt(...)`, a blank line, and `LANGUAGE (highest priority): ` plus `PromptBuilder.LanguageInstruction(language)`. No other system-role message is sent anywhere in the request (history and replayed tool rows only contain user, assistant and tool messages). The detection is still deterministic and stored in `ChatSession.Language` before every run (SPEC 7.3). The last common rule (12 since M8 added the knowledge-base and offer-a-person rules as rules 2 and 3) points at the LANGUAGE line.
- **Alternatives:** append the instruction to the last user message or send it as a trailing user-role message (closest to the model's attention, but it pollutes the history and the trace with text the customer never wrote, and a user-role instruction is easier to override by prompt injection); keep two system messages for providers that accept them (a provider-specific code path to test, and the demo runs on Gemini); drop the instruction and trust the persona prompt (the v1 bug SPEC 7.3 exists to prevent).
- **Consequences:** Deviates from SPEC 7.3 ("last system message"): the instruction is the last paragraph of the only system message, which is after all persona text but before the conversation. Models may weigh it a bit less than a message right before the user turn. Revisit with the user-role suffix if the language evals (100 % target) show weaker adherence. `TracingChatClient` already skips the first (system) message in the stored input, so the trace shows no prompt text.


## ADR-015: RAG only for free text; the catalog stays on filters
- **Context:** M8 adds questions the catalog cannot answer: "do you accept pets?", "what if I cancel the appointment?", "which insurance plans?", "is the gluten-free dough cooked apart?". Their answers live in prose documents (15-25 per business), not in rows. ADR-007 decided the opposite for the catalog: 28 structured offerings searched with filters.
- **Decision:** Two techniques, chosen by the shape of the data. Structured data (offerings, prices, availability, bookings) is queried with exact filters through the catalog tools, and the prompt still requires prices and availability to come from those tools in the same run. Free text (policies, conditions, FAQs, requirements, allergens, delivery zones) is retrieved with `search_knowledge_base` (hybrid search, ADR-016) and the model answers only from the returned passages. A mixed question ("does the Palermo apartment accept pets?") uses both tools. The passages are delimited, declared untrusted data in the result and in the prompt, and cited naturally ("according to our cancellation policy..."); a search with nothing above the relevance threshold returns `found: false`, and the agent says it has no information and offers a person instead of answering from memory.
- **Alternatives:** RAG over the catalog too (approximate matching returns the wrong price or item for an exact filter like "2 rooms in Palermo under 600", and a price from a retrieved chunk is not the price in the table); the whole knowledge base in the system prompt (15-25 documents per business on every call: tokens and cost on every message, no retrieval trace, and the persona prompt is already long); fine-tuning (out of scope and stale on every edit); keeping the policies as `BUSINESS FACTS` lines of the persona (what the first version did: it cannot grow, and the model answers from it without searching).
- **Consequences:** ADR-007 still holds for the catalog and is not superseded. The persona `BUSINESS FACTS` blocks (hours, "accepts most insurance plans") were left in place: they overlap with some documents and the agent may answer from them without searching; remove them if the evals show it. A retrieval can be wrong or empty, so the quality of answers now depends on the retrieval evals (recall@4, MRR) as well as on tool use. Every `search_knowledge_base` call costs one embedding request on top of the model calls.

## ADR-016: Hybrid search (vector + full text) fused with Reciprocal Rank Fusion
- **Context:** Customers ask in natural language ("can I bring my dog?") and with exact strings ("OSDE 210", "USD 300", "48 hours", "sin TACC"). Vector search finds meaning across languages but ranks a short exact token poorly inside a long chunk; full-text search finds the token but not paraphrases or the other language. The documents mix Spanish and English (ADR-017).
- **Decision:** `KnowledgeSearch` runs two rankings of 20 chunks, both filtered by `BusinessId` in SQL: semantic (cosine distance on the HNSW index) and lexical (`ts_rank` of `websearch_to_tsquery('simple', ...)` on a generated `tsvector` of heading and text, GIN index). They are merged with Reciprocal Rank Fusion (`score = sum 1/(60 + rank)`) and the best 4 are returned with their semantic, lexical and final scores, which the `Retrieval` trace event shows. RRF uses positions only, so it needs no score normalization between a cosine similarity and a `ts_rank`, and an item found by one ranking alone still scores. The lexical query is the question reduced to its content words (`LexicalQuery`, common Spanish and English words dropped), which `websearch_to_tsquery` ANDs: a chunk is a lexical hit only if it contains every one of them. `simple` is the text search configuration because it is the only one that fits two languages at once (no stop words, no stemming). Relevance is a threshold: a passage counts when its cosine similarity reaches `Knowledge:MinSemanticSimilarity` or its `ts_rank` reaches `Knowledge:MinLexicalRank`, so an exact code that the embedding scores low still passes. **Measured, not guessed** (28 answerable questions in Spanish and English, half of them about a document in the other language, plus 19 unanswerable ones, against the 54 real documents and `gemini-embedding-001` at 768 dimensions; a throwaway probe, the committed retrieval evals will replace it): fusing the semantic ranking with an OR lexical query gave recall@4 0.86 and MRR 0.78 (common words such as "separately" or "cooked" matched English chunks and, by agreeing with the semantic ranking, pushed the right Spanish document out of the top 4); the semantic ranking alone and the semantic + AND-lexical fusion both gave recall@4 1.00 and MRR 0.98. So the lexical side is an AND query: it adds nothing to a natural question (no chunk contains all its words, no lexical hits) and takes over for exact strings. The best semantic hit of every answerable question scored at least 0.62 (most above 0.70), the best hit of the unanswerable ones between 0.45 and 0.68 (those at or below 0.58 are clearly unrelated; "do you deliver to the moon?" or "do you treat dogs and cats?" reach 0.61, being close to the topic of a real document). That is why the defaults are `0.60` and `0.05` (a lexical hit already contains every content word, so the bar is low); the rest of the filtering is the agent's job, which answers only from passages that really answer the question (prompt rule 2). The numbers depend on the model and the dimensions: retune them whenever either changes.
- **Alternatives:** vector only (misses acronyms, amounts and proper names that the embedding blurs; the SPEC asks for exact text to be findable); full text only (no paraphrases, no cross-language); a weighted sum of normalized scores (a tuning parameter whose scale shifts with the corpus); a cross-encoder reranker (another model call, latency and quota for a corpus of under 100 chunks per business); one text search configuration per language (needs a language per query and per chunk; the unaccented, unstemmed `simple` index is good enough for exact tokens).
- **Consequences:** `simple` has no stemming, so "cancelar" does not match "cancelación" lexically (and an AND query with an inflected word finds nothing); the semantic side covers it. A fusion score is only an ordering, so the threshold needs the two raw scores, and a threshold tuned on the real model does not transfer to another embedding model. The two queries run one after the other on the request's `DbContext` (a few milliseconds; parallel would need a second connection). Covered by `ReciprocalRankFusionTests`, `LexicalQueryTests` and `KnowledgeSearchTests` (an exact code the fake embedding does not score above the threshold is found lexically, and is not without the lexical side).

## ADR-017: pgvector in the same PostgreSQL, 768 dimensions, `gemini-embedding-001`
- **Context:** M8 needs vectors next to the relational data (SPEC 4 rules out a separate vector database), an embeddings model reachable with the key the project already has, and documents in two languages queried in either.
- **Decision:** (1) **Same database.** `pgvector/pgvector:pg17` replaces `postgres:17` in Docker Compose, in the Testcontainers fixtures and in the evals throwaway database (the data directory format is the same, so an existing `pgdata` volume keeps working). The `KnowledgeBase` migration runs `CREATE EXTENSION vector`, creates `knowledge_documents` and `knowledge_chunks` (`Embedding vector(768)`, `EmbeddingModel`, generated `SearchVector`), an HNSW index (`vector_cosine_ops`), a GIN index on `SearchVector`, an index on `BusinessId` and a unique `(DocumentId, Ordinal)`, and adds `Retrieval` to the CHECK constraint of `trace_events.Type`. Mapped with `Pgvector.EntityFrameworkCore` 0.3.0 (built against EF Core 9 / Npgsql 9; it works with EF Core 10 and Npgsql 10 here, and the whole model builds and migrates in the tests). (2) **Model.** `gemini-embedding-001` through the OpenAI-compatible endpoint (`POST {BaseUrl}/embeddings`), on the same key as the LLM, so no new secret. It is multilingual: the same question in Spanish and in English gets a cosine similarity of about 0.86, which is what lets an English question find a Spanish document. (3) **768 dimensions.** The model returns 3072 by default and honors the OpenAI `dimensions` parameter (Matryoshka representation learning: the first N components are a valid embedding). pgvector indexes (HNSW) accept at most 2000 dimensions, so 3072 could not be indexed; 768 keeps recall close to the full vector for a few hundred chunks and costs a quarter of the storage. `Embeddings:Dimensions` is sent on every request, the `Embedder` rejects vectors of another size, and the options validation refuses a value different from the column size (`KnowledgeSchema.EmbeddingDimensions`). Changing it means editing that constant, adding a migration (the column type) and re-indexing; changing the model re-indexes automatically because the model and the dimensions are part of each document hash and each chunk stores its `EmbeddingModel`, and search filters by the current one, so vectors of two models are never compared. (4) **Documents.** Spanish and English mixed on purpose (no duplicates), to exercise cross-language retrieval, in `Seeding/knowledge/<niche>/*.md` (`realestate`, `dental`, `restaurant`), next to the existing `Seeding` folder with the personas, and not in `Seed/knowledge` as the SPEC says. They are embedded resources of the Infrastructure assembly, so `dotnet run`, Docker and tests read the same files.
- **Alternatives:** Pinecone, Qdrant or another vector database (a second service to run, secure and keep in sync for under a few hundred chunks); 3072 dimensions with a sequential scan (works at this size but gives up the index the project is meant to show; a half-precision index (`halfvec`, up to 4000 dimensions) would, at the cost of a different type mapping); OpenAI `text-embedding-3-small` (another provider, another key and a billing account; the Gemini key is free); a local model (out of scope); the `gemini-embedding-2` model that the Google pricing page now lists (multimodal, not verified on the OpenAI-compatible endpoint here); duplicating every document in both languages (doubles the content and hides whether cross-language retrieval works).
- **Consequences:** Pricing: `ModelPricing` has no row for `gemini-embedding-001`. On 2026-10-10 the Gemini pricing page lists only `gemini-embedding-2` ($0.20 per 1M text tokens on the paid tier, free on the free tier) and does not list `-001`, so no price could be verified and none was invented: the embedding cost shows as 0 and `Retrieval` events say so through `costUsd: 0`. Add the row by hand when the price is known (the run cost then includes it). The free tier rate limits embeddings by minute, so the first ingestion of the whole corpus can take a while (the `Embedder` backs off on 429); later runs skip unchanged documents and cost nothing. An HNSW index with a `WHERE BusinessId = ...` filter is applied after the index scan, so with many businesses the filtered top 20 can contain fewer than 20 rows (pgvector 0.8 has iterative scans for it); with 3 businesses and hundreds of chunks the planner may also choose an exact scan. Not a concern at this size; revisit with partitioning by business or `hnsw.iterative_scan` if it grows. The dimension is a compile-time constant of the schema, not a purely runtime setting: that is the price of a typed column and a real migration.
